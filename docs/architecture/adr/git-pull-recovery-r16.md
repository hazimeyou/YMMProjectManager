# ADR: R16 Git Pull の更新と回復の境界

状態 **書き込みは BLOCKED。読み取りによる状態確認を強化**。

## 契約

Pull を有効化する条件は、承認済みの物理リポジトリ、リモート、枝、開始コミットを固定し、fast-forward 以外の履歴を拒否した上で、ref・index・作業ツリーの状態を一体で回復できること。既存の変更や未追跡ファイルの退避を利用者の許可なしに行わない。中断後にどの段階まで更新したか判別できない場合は、後続の更新を起動せず復旧対象を示す。

Git の個別のロック、ディレクトリの物理 ID、読み取り前後の比較だけでは外部 Git やエディターの操作と排他できない。現行の WPF コマンドはローカル保存済みの追跡 ref から状態を表示する。書き込み API は Git の起動前に明示エラーを返す。状態確認でロックや未完了操作、index が変更を隠す可能性、submodule、構成済みの filter が見つかった場合は作業ツリーの状態を推測しない。状態確認は特定時点の観測であり、将来の更新の許可には使用できない。

## 比較結果

Git for Windows 2.55.0.windows.5 と Windows の一時領域で、合成ファイルだけを含む独立したリポジトリを使用した。

| 方式 | 実測または仕様 | 判断 |
| --- | --- | --- |
| アプリ自身のロック | アプリ専用ファイルを排他的に開いたまま、別の Git プロセスで合成リポジトリの枝を切り替えられた。 | 複数プラグイン操作の調整にしか使えない。Git クライアントやファイル編集の排他を追加できない。 |
| 分離した index と worktree | `GIT_INDEX_FILE` と `--work-tree` を両方別領域へ向け、`git read-tree -m -u` を使用すると、ステージ側だけに候補の内容を作れた。元のファイル、index SHA-256、HEAD は変わらなかった。 | 候補の作成と検証には使える。元の ref、index、ファイルを一緒に切り替える処理が残る。 |
| ディレクトリ単位の公開 | 空でない既存ディレクトリへの `Directory.Move` は拒否され、候補と元の内容は保たれた。Windows の公開 API も既存ディレクトリの置換を一般には提供しない。 | 旧ツリーを先に動かす二段階の交換では、間に中断すると既存のパスを失う。別ディレクトリへの公開は既存 checkout の Pull として扱わない。 |
| Git のネイティブな ref トランザクション | Git の `update-ref --stdin` は ref を対象とする。R15 では HEAD のロックが `merge --ff-only` による index とファイルの先行更新を止めなかった。 | ref を単独で変更したり、ref のロックを全体の巻き戻し手段として使ったりしない。 |

仕様資料として [Git read-tree](https://git-scm.com/docs/git-read-tree)、[Git update-ref](https://git-scm.com/docs/git-update-ref)、[Windows FILE_RENAME_INFORMATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) を参照。R15 の観測は [Git 操作の信頼境界](git-trust-model-r4.md) に記録。

## 復旧方針と再開地点

現行の書き込み API から発生する部分更新はない。状態確認で別プロセスの未完了操作が見つかっても、その lock や marker を削除しない。作業ファイルを保全し、操作を開始したクライアントで状態を確認する。未知の書き込みや枝の切替後は状態を確認し直す。

次は、対象 checkout への外部書き込みを止める仕組みと、作業ファイル・index・シンボリック HEAD・対象 ref の照合結果を保持する復旧契約の組を検証する。開始前、候補作成後、最初の公開後に所有プロセスを停止し、既存ファイルが保存されることを個別に確認する。直接の checkout を安全に更新できない限り、書き込む Pull は無効とする。別ディレクトリを使う Git 更新ワークフローは別の製品判断を必要とする。
