# ADR R18 — Git Pull の候補公開と中断時の保全

この資料は R18 の判断を記録する。利用者の承認を受けた後続の実装と適用範囲は R19 に記載。 [R19 確認付き fast-forward Pull](git-pull-confirmed-r19.md)

状態 **既存の作業ツリーに反映する Pull は BLOCKED**。候補公開方式の変更は製品判断待ち。

## 判断条件

利用者が承認したリポジトリ、remote、対象 branch、旧 commit、新 commit を操作中に一致させる。追跡 ref の現在値や置換された履歴を承認済み commit の代わりに使用しない。公開後は対象 branch の ref、新 commit の tree と index、作業ファイルの分類が一致することを確認する。変更対象と重なる未追跡・無視対象、未コミットの利用者データ、外部プロセスが所有するファイルを保持する。

R17 では HEAD の実ファイルハンドルで更新を拒否しても index と作業ファイルが先に変化することを実測した。Git の ref のロックだけ、管理用 worktree lock、アプリ内 mutex で三者の一貫性を証明できない。[R17 の実測](git-pull-recovery-r17.md)

## 合成検証

2026-11-21T00:46:27.3968373+09:00 から 2026-11-21T00:46:29.2918194+09:00。Git for Windows 2.55.0.windows.5、ローカル NTFS。合成 bare remote とローカル checkout を利用した。通常のようにプロジェクトを開く処理は含まない。

| 方式 | 防止・検出条件 | 中断と回復 | 実測と判断 |
|---|---|---|---|
| 別パスに独立 checkout を公開 | clone・checkout はアプリの一時領域だけを変更する。候補の commit、index の tree、clean 状態を検証し、親ディレクトリを同一ボリュームに固定する。存在する最終パスへの公開は拒否する。 | 公開前の中断時は元 checkout を変えず、残存候補の所有権と識別子を確認してから回収する。公開後は候補の識別情報で照合する。 | `clone --no-local` で作った候補を新しい兄弟ディレクトリに移動した。候補 HEAD は新 commit、index tree は新 commit の tree、状態は clean。元 HEAD と index の SHA-256、追跡済み編集と未追跡素材の内容は一致した。既存パスを維持する Pull の代替にする場合は、明示的な利用者承認とプロジェクト再関連付けが必要。 |
| 既存パスを退避し、候補を公開 | 上記の候補検証に加え、変化していない元 checkout と排他的な管理対象を特定する。退避先、候補、公開先の所有権と操作 ID を記録する。二つの rename の間は元のパスが空く。 | 旧版退避直後に子プロセスを終了コード 91 で終了した。起動し直す処理は、意図記録と元・退避・候補の識別情報が一致する場合のみ次の操作を選択できる。元パスを外部が確保した場合は既存の全パスを保持し人手での復旧に引き継ぐ。 | 元パスが一時的に消えた。別処理が同じパスを作ると候補からの `Directory.Move` は拒否され、退避版、候補、別処理のファイルが残った。退避版の HEAD、index、追跡済み編集、未追跡素材も一致した。操作の継続に協調的な排他と永続記録が必要。 |

別パス方式でもリンクした worktree、サブモジュール、外部 config、YMM4 の開いているファイルに対する自動的な再関連付けは別途検証と承認を要する。退避方式の子プロセス終了は rename 間の中断点を再現する。電源断、ネットワークファイルシステム、別プロセスの継続中ハンドル、共有 checkout 全体の排他は未検証。二つの rename を一つの分離されたトランザクションとして扱える根拠は得られなかった。[Git clone](https://git-scm.com/docs/git-clone) [Windows MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)

## 外部プロセスと取消しの境界

| 外部の動作 | 別パスへの公開 | 退避と復旧 |
|---|---|---|
| 元 checkout の枝切替・編集 | 元 checkout への書き込みがないため、利用者の操作を妨げない。候補を既存プロジェクトへ関連付ける製品機能を追加する場合は、その決定時に旧状態の再確認が必要。 | 承認と旧状態の記録の後に変更され得る。管理者・YMM4・外部 Git の協調を検証できる場合のみ許可。協調契約のない変更は現在の安全範囲外。 |
| 第三者が候補の公開先を確保 | 上書き不要の公開で拒否し、既存の対象と候補を保持する。 | 元パスが再作成された場合、復旧で上書きしない。候補と旧版をそのまま残して競合を報告する。 |
| 取消し・中断 | 準備中は取消し可能。公開開始後は実際の候補の所在と ID を調べて結果を確定する。 | 旧版退避まで取消し可能。退避以降は一時停止として記録し、同じ処理を盲目的にやり直さない。 |

別パスの方式は所有範囲が小さく、保守と検証を限定できる。利用者には新しいパスが見え、元 checkout の Git 設定やプロジェクト一覧・素材参照の継続方法が必要。退避方式は既存パスを維持し得るが、アプリ外の読取り・書込みを含む排他、持続的な操作記録、競合を保存する復旧 UI が必要。製品判断を変更する両案の状態は **APPROVAL_REQUIRED**。既存の診断・Clone・Fetch・Push を現状の経路で提供する。

公開処理が進行中の場合の timeout・アクセス拒否、プロセス強制終了後の永続ジョブ再開は両案とも製品経路では未実施。合成結果は本文の子プロセス終了直後の内容確認まで。既存の `PullAsync` は変更前に `UnsafeOperation` を返す。失敗を判定できない場合は対象を保持し、利用者の変更を勝手に巻き戻さない。

## 今回の実装と残る判断

- `InspectPullAsync` は置換 ref に加えて、実行環境とリポジトリの graft による履歴の付け替えを考慮する。Win32 の Git で `GIT_NO_REPLACE_OBJECTS` 単独では graft の影響が残ることを合成履歴で確認した。graft を含む作業ツリーは `HistoryNotVerifiable` とし、比較中に graft が現れた場合は再確認を要求する。系譜比較を示せない場合は更新候補の表示を避ける。[Git repository layout](https://git-scm.com/docs/gitrepository-layout#Documentation/gitrepository-layout.txt-infografts)
- `InspectPullAsync` はネットワークに接続せず、ローカルの追跡 ref を再検証する。合成 bare 側の移動は fetch 前のキャッシュ表示を変えなかった。二回の観測の間にローカル追跡 ref を移動・削除すると `Changed` を返し、次の検証は `UpToDate` または `TrackingUnavailable` を返した。HEAD、index SHA-256、作業ファイルを維持した。
- 既存の branch switch に対し、追跡対象への切替で上書きされる無視ファイルを保持する回帰テストを追加した。通常の切替は合成 checkout で継続確認する。
- 読み取り診断の `git status` はオプションの index 書き込みを抑止している。有効なフィルターを先に別の Git プロセスで確認しており、その確認から `status` の設定読込までに実効設定を変えられる。既存診断の境界として残る。作業ツリー状態を引き続き診断するには、固定した許可リストの設定で同じ判定を再現するか、明示の信頼契約を設計する。
- 既存 checkout への Pull を再開するには、アプリ外の操作を含む参加者とファイルシステムの範囲を明文化し、確認済みの範囲で ref・index・ファイルの回復契約を実装する。別パスの検証済み checkout を提供する場合は、新機能として承認と再関連付けの契約を定義する。
