# 設計思想（暫定）

この版は v0.5.0 のユーザー調整用の出発点である。MUST は既存データや公開契約を守る必須事項、SHOULD は例外に理由を記録する原則、MAY は個々の変更で判断できる選択を示す。

## 目的と構成

- **MUST** 変更前に、利用者が操作を開始する入口、対象を承認する時点、ディスクや外部プロセスに副作用が生じる時点、失敗後に残る証拠を特定する。
- **SHOULD** 一つの機能を変更するときに一緒に読むコードを近くに置く。例えば `Ymmpx/` では受け渡し計画、パッケージ検査、出力、WPFの同梱確認を辿れる。トップレベルのフォルダーは製品の機能名を基本とする。
- **MAY** 大きい機能では、用途が明確なまとまりを分ける。例えば `Git/UI/` は利用者への確認、`GitRepository.Process` はプロセスの起動・入出力・終了の担当である。フォルダーを揃えるための空の層は作らない。

## 共通化とクラス分割

- **SHOULD** 共通化前に二つ以上の実際の呼び出し元を読み、入力、結果の形式、取消、資源の所有権が同じか確認する。素材プールと再リンク回復はどちらも、呼び出し元が開いたストリームから完全な大文字16進SHA-256を必要とする。ファイルの承認、ロック、位置決め、解放は各操作が担当する。
- **MUST** 照合の対象を明確にする。同じバイト列でも独立コピーは別のProject Identityになり得る。内容のハッシュ、元の素材名、物理ファイルID、リビジョン、利用者の承認は個別の証拠である。
- **SHOULD** 分割の単位は一緒に変わる振る舞いで決める。Gitプロセスの入出力を読むために承認済みPushの処理を読み解く必要はない。一方、確認と再検証の順序は同じワークフローで追えるようにする。
- **MAY** 一つのWPF画面が選択・取消・未保存状態を共有する場合、partialで機能別のコマンド実装を配置する。独立したサービスへの分割は所有する状態と終了時処理を説明できる場合に行う。partial自体は依存性を隔離しない。

## 命名と定数

- **SHOULD** 操作と対象を名前に含める。`ProjectListYmmpxTransfer` は担当する操作から検索できる。開発フェーズ名は履歴や引き継ぎの名前に使う。
- **SHOULD** 64 MiB のPF読取上限のように、値を変えると利用者が扱える範囲が変わる数値には用途を示す名前を付ける。件数0、添字1、表示レイアウトに共通の「定数クラス」は作らない。
- **MUST** 保存形式、公開型、WPFバインディング、リフレクションで取得する名前の変更は、利用側と互換性への影響を調べる。

## 依存関係とUI

- **SHOULD** UIで入力・明示確認・状況表示を行い、ファイル公開、Git実行、取得済み証拠の再検証は各機能のサービスで完結させる。バックエンドからWindowやMessageBoxを呼ばない。
- **MUST** 待機中に選択・ファイル・ブランチが変わり得る箇所で、承認対象を実行前に再照合する。GitHubの閲覧可否は、匿名の公開リポジトリでも成功する。UIはその結果でログインを確定しない。
- **MAY** ホスト依存や複数機能で共有する境界を独立配置する。所有ファイルの公開は `Shared/Files/` に置き、素材の再配布許諾やGit公開可否の判断を持ち込まない。

## 例外・データ保全

- **MUST** 保存失敗と取消を呼び出し元へ伝える。公開後の状態が不明なときは回復記録と出力を保持し、物理ID・ハッシュ・操作ID等の対応する証拠で再照合する。再試行だけで成功扱いにしない。
- **MUST** PF整理では既知の対象だけを変更し別名保存する。厳格再リンクでは元の名前と完全SHA-256を照合し、素材プールの短縮名は照合の根拠に使わない。YMMPXの同梱許諾とGitのStage・Commit・Push前の公開検査を維持する。
- **MUST** Gitの承認済み接続先、GCM検証、非force Push、fast-forward Pullのref・index・worktreeの整合性を維持する。標準入出力や診断に資格情報を残さない。
- **SHOULD** サムネイルのように回復可能な補助機能の失敗は、その影響範囲で記録・表示する。データ保存の失敗を同じ扱いにしない。

## 例と適用方法

良い例は、承認済みストリームに対して素材名、サイズ、内容を別々に検証することである。以下は照合の抜粋で、シーク可能なファイルハンドルを所有する呼び出し元が公開直前まで保護する。

```csharp
if (!string.Equals(originalName, expectedName, StringComparison.OrdinalIgnoreCase))
    return false;
if (approvedStream.Length != expectedSize)
    return false;
approvedStream.Position = 0;
var actualSha256 = await AssetContentHash.ReadSha256Async(approvedStream, token);
return approvedStream.Length == expectedSize &&
    string.Equals(actualSha256, expectedSha256, StringComparison.OrdinalIgnoreCase);
```

悪い例は `return actualSha256 == expectedSha256 || originalName == expectedName;`。同名の旧版と、別名にした同内容の素材の両方を誤って採用し得る。型を分けたり短く書いたりしても、この条件は修復されない。

- **MUST** データ保全に関わる変更は合成fixtureで確認する。成功結果に加え、中断、置換競合、再実行時の元データ・出力・回復記録を検査する。実ホストと合成試験の受入結果は個別に記録する。
- **SHOULD** 関連する重点試験を変更単位で実行する。統合後はRelease・Debug、実YmmpxLibの有無で回帰し、失敗・条件付きスキップと試験対象HEADを記録する。
- **SHOULD** 独立レビューで GOOD / IMPROVE / RECONSIDER / REJECT の根拠を示す。対象、現状、影響、優先度、代案、対応結果を残す。好みだけを根拠に変更しない。
- **MAY** WPFリソースの物理配置を維持する。既存のpack URI、BAML、型の完全名を参照するコードがある場合、機能別フォルダーへの移動より互換性を優先する。
- **SHOULD** 次の機能変更では該当機能のテストとADRから開始し、上記判断に例外が生じたら理由・試験・復帰方法をレビューに記録する。ユーザー調整後に正式な方針を決める。
