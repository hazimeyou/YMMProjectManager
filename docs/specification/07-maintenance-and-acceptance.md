## 変更時に維持する契約

1. **論理ID・物理ID・版・内容**。Project IDは論理的な関係、物理ファイルIDは開いて検査した実体、SHA-256はバイトの版を表す。論理上の移動・改名・派生の決定は利用者の確認に結び付ける。[Identity](02-project-data.md#論理idとファイルの照合)
2. **確認から公開まで**。承認対象のハンドル、パス、ディレクトリ、リビジョン等を操作の性質に応じて再照合する。新規出力は非上書き。既存一覧・設定を更新する場合は保全と中断回復を含む既存契約を使う。[設計思想](../architecture/DESIGN_PHILOSOPHY.md) · [一覧の公開ADR](../architecture/adr/project-list-publication-r17.md)
3. **取消・失敗・結果不明**。回復記録を使って成否を識別し、外部版や確認済み出力を保持する。シークや描画が遅れて完了した場合は、選択・対象版・フレームが現行かを確かめて結果を採用する。[ホスト連携](04-host-operations.md#タイムライン比較プレビュー) · [派生再リンクADR](../architecture/adr/external-relink-derivation-r22.md)
4. **素材のローカル処理とGit公開**。再リンクでは元名と完全SHA-256を両方要求。YMMPXの同梱先は利用者が選んだローカル出力。Gitは既知の素材本体・素材入りパッケージや秘匿データを公開前に拒否する。[Git・YMMPX](03-git-ymmpx.md)
5. **公開名と形式の互換性**。保持すべき名前には公開型、WPFのリソースやバインディング、リフレクションで解決するメンバー名、保存ファイルのキーと版が含まれる。移行が必要になった場合は互換読込みと復旧を明示し、試験で対象の旧形式を固定する。[設計の互換性規則](../architecture/DESIGN_PHILOSOPHY.md)

## 旧仕様と現行の境界

| 旧仕様・説明 | 現行の扱い |
| --- | --- |
| 独自世代の作成・一覧・削除・復元 | R32で廃止。既存の世代はサイズとSHA-256を照合し別名PFに救済できる。[旧世代ADR](../architecture/adr/legacy-generation-export-r32.md) |
| 単独のPF整理 | R32で画面と専用処理を撤去。YMMPX作成で利用者が選ぶUI状態の扱いは同梱するPFコピーに適用する。[R32仕様判断](../development/v0.5.0-r32-spec-integration.md) |
| PM独自許諾による新規YMMPX作成 | R32で標準形式とPackagerの素材選定・除外方針を採用。旧PM v1/v2の許諾を含む目録は互換読込みの対象。素材プールの権利記録は利用者が記録する任意項目。[YMMPX仕様](03-git-ymmpx.md#ymmpx) |
| 展開の確認ダイアログにある「新しい受け渡し用YMMPXは…目録と照合」 | 現行標準の出力は単体の `.ymmpx`。隣接目録を必須にするのは旧PM形式を識別した場合。ダイアログに旧仕様に沿う文言が残っている。[確認ダイアログ](../../YMMProjectManager/Ymmpx/UI/ProjectListYmmpxImportExport.cs#L57) · [形式の識別](../../YMMProjectManager/Ymmpx/YmmpxPackageReader.cs#L119) |
| YMM4内のTimelineシーク・キャプチャ・直接変更を扱うコード | 一部は診断・合成試験と将来の接続に使う基盤。保存済み画像は表示できる。実Scene描画とTimeline直接反映はホスト契約を実証するまで停止。[ホスト仕様](04-host-operations.md#タイムライン比較プレビュー) |

## 確認と受入のチェックリスト

| 確認項目 | 現在の証拠・残る条件 |
| --- | --- |
| コード・型目録の更新 | 機能のUI入口、所有する状態、サービス、保存形式、正常・取消・競合のテストを追跡する。ソースを変更した場合は型の宣言行と仕様の基準HEADを更新 |
| 実行を伴う変更の回帰 | 隔離したYMM4参照を使う。製品と試験のRelease・Debug、実YmmpxLibあり・なし、変更した機能の重点試験と実行HEADを記録。R34の4構成は終了0。現仕様書作成時の確認は構文解析、リンク、静的レビュー |
| R35の固定6工程 | 管理側R16定義は旧ソースと旧DLLを固定。候補の新規定義・SHA-256照合、新規の隔離ステージ、操作と回数の承認、隔離・Recovery・起動直前の確認が必要。[VM受入依頼書](../development/v0.5.0-r34-vm-request.md) |
| R35で使う起動証跡 | R15管理側の既存判定は一覧読込みの開始・完了のメッセージ本文を探す。現在のPMは本文をログAPIへ渡し、ファイルには自由文を保持しない。管理側で開始と完了を区別できる観測を再検証する。[ホスト仕様の受入確認](04-host-operations.md#試験受入の状態) |
| 実YMM4での機能別確認 | 正式環境でYMMPXと除外、保存済みキャッシュ、比較、旧データ、回復を用途ごとに検証する。独立Sceneの読込み、所有、GPU資源の解放を証拠化してから新規取得・左右描画を審査。直接反映はUndo/Redo・未保存編集・途中失敗の保全を別途確認。[R34のシナリオ](../development/v0.5.0-r34-scenarios.md) |
| 実GitHub認証 | 実アカウントと専用リポジトリの承認を伴う接続先で検証する。隔離HTTPSは認証フローの契約試験。NICを切断した既存受入VMの範囲と個別に扱う。[認証と試験状況](03-git-ymmpx.md#検証記録と残る確認) |
| 対応範囲の判断 | Windows 10、別YMM4版、NAS、SSH、YmmpxLibの別配布版を保証対象にする場合は、方針の承認と組合せ別の受入が必要。実施済みの環境と版は個別に記録する。[対応方針](../../README.md) |
