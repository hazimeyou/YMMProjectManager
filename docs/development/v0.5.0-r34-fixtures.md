# R34 合成受入データ

## 生成と照合

PMの受入用入力をホストのローカル一時領域に新規生成する。実ユーザーのPF、素材、設定、キャッシュは入力に使わない。YMM4での読込状態は全データで `NOT_VERIFIED`。正規のYMM4で保存した試験専用PFが必要な手順は、承認後に管理側で対象を作成し、そのPFの完全SHA-256を採り直す。

Windowsでは固定ローカルドライブ上の `%LOCALAPPDATA%\Temp` へ生成する。UNC、デバイスパス、代替データストリーム、リパースポイントを拒否する。POSIXではPythonが解決する一時ディレクトリを使う。

リポジトリルートでPython 3.11以降を使う。標準YMMPXを生成する場合は .NET 10 SDKと隔離済み公式YmmpxLib 1.1.0 DLLが必要。旧形式はR23の公開版CLI由来の合成アーカイブを渡す。オプションを省略したアーカイブはmanifestの `unavailable` に記録される。

```powershell
python -B scripts/r34_fixtures.py create --ymmpx-lib $isolatedLibrary --legacy-root $releasedSyntheticPackages
python -B scripts/r34_fixtures.py verify $fixtureRoot $approvedManifestSha256
python -B -m unittest discover -s scripts -p test_r34_fixtures.py -v
```

出力の `root` は新規ディレクトリ、`manifest_sha256` は承認対象へ別記するハッシュ。manifestに各ファイルの相対パス、バイト数、SHA-256と、fixture単位の生成元、期待結果、削除可否、実機読込状態を保存する。コピー後は承認済みのmanifestハッシュを使用して再照合する。承認済みfixtureを別のファイルで上書きした場合、同じサイズでも照合は失敗する。期待された欠落が埋まった場合も失敗する。検証スクリプトは静止したローカル合成領域が対象で、実行中の入替えに対する排他はVM管理側が担当する。

R34で照合したローカル出力は `%LOCALAPPDATA%\Temp\p34f-ibt8ivrt`。manifestのSHA-256は `6e3f6a8aeb9c31dca9a507935d040465cf251f43b9da1ff254f28229b9dc9c8e`、照合済み入力は94ファイル。再生成では生成先の絶対パスやZIPのタイムスタンプが変わるため、新しいmanifestを採用して承認用ハッシュを取り直す。

| ID | 主な入力ファイル | 生成内容と合格条件 |
|---|---|---|
| PF-A | `pf/a.ymmp` と色板PNG | 24 fps、130秒相当。0、60秒・120秒の前後、終端の目印を区別する |
| PF-B | `pf/b.ymmp` と色板PNG | 30 fps、140秒相当。Aと論理Scene IDが一致し、PFのSHA-256、版、フレーム位置、色板が異なる |
| PF-C | `pf/c.ymmp` と色板PNG | 2個のSceneのID、素材、長さが異なる。対象外のSceneとの取り違えを検査できる |
| PF-D | `pf/d.ymmp`、`relink/expected-material.json`、`relink/exact`、`relink/wrong-bytes`、`relink/wrong-name` | `missing/clip.png` が欠落している。期待名と完全SHA-256に一致する候補は1件。同名・異内容と異名・同内容を拒否する。期待値JSONは試験用 |
| PF-E | `pf/e.ymmp`、`pf/a.ymmp`、`thumbnails/000.png`〜`063.png` | 1フレーム相当と長尺の組。連番PNGは64点分の異なる画像。順序、上限、取消後の破棄を確かめる |
| COMPARE | PF-A／B、`compare/fixed.json`、`compare/sections.json` | 比較設定v1の固定+2秒、区間なし−2秒、60秒から+10秒、120秒から−5秒。端点の包含・範囲外・再読込を確かめる |
| EXCLUDE | `exclude/import.json`、`exclude/invalid.json`、標準YMMPX用PF | 正常な除外ルールは `media/still.png` を指定。同一プロパティが重複した入力は拒否し、既存設定とPFを保持する |
| LEGACY-LIST | `legacy/projects.json` とPF-A／B／C | 重複IDの2行とIDなしの1行。既存の元データ、残すID、未知のルート・リンク項目を確認する |
| LEGACY | `legacy/current.ymmp`、`legacy/Generations/projects/…/manifest.json` と `generations/<ID>/metadata.json`、`project.ymmp` | 破損した世代manifestは保持する。世代のサイズとSHA-256を照合して別名PFに出力する |
| YMMPX-PF | `ymmpx/standard.ymmp`、`media/still.png`、`shot01.png`、`shot02.png`、`layers.psd` | 通常のPNG、連番PNG、PSDレイヤー参照、欠落素材、UI項目、未知項目。同梱ルールと非上書き・取消を個別に判定する |
| YMMPX-1.1 | `ymmpx/standard.ymmpx` | 公式YmmpxLib 1.1.0のAPIで生成。PF、リンク、マーカーと4素材を確認し、素材バイト・PSDレイヤー参照・欠落参照・未知項目の期待値を検査 |
| YMMPX-v0.2.1／v0.3.0／v1.0.1 | `ymmpx/legacy/<版>/sample.ymmpx` | R23で各公開版CLIから作成された既知SHA-256の合成サンプル。PMで旧形式として識別して展開し、元アーカイブを保持する |

標準ファイル生成時の検査は、期待したアーカイブ項目名、素材バイト、PF内の参照を確認する。別途、候補DLLの公開展開APIで標準1件と旧版3件を合成試験し、4件とも展開できた。公式ライブラリが生成した標準ファイルでは欠落参照が相対パスのまま保持され、展開APIの明示欠落リストは空だった。欠落の明示通知はPM側で作成したパッケージのシナリオで判定する。

実機では試験専用の保存場所で新規作成・新規出力し、コピー元を保持する。LEGACYの `SourceProjectPath` とLEGACY-LISTの `FullPath`・`FilePath` は生成先の絶対パスを持つ。別ルートへの持ち込み時は試験専用コピー内の参照を差し替え、変更後の新しいハッシュと対応表を記録する。旧キャッシュの表示試験で64点素材を使う場合は、隔離キャッシュ内で `FilmstripCacheKeyFactory.TryCreateHash` が指定する対象PF・更新時刻用の場所へ採用し、保存済み旧キャッシュとして扱う。入力画像の合成は実Scene描画の証拠には使わない。

試験用コピーだけを後から削除できる。Runの回収証拠、承認済みハッシュ、以前のRunに属する出力、隔離元のDLLと旧形式サンプルは保持する。
