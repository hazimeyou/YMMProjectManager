## Pull の判断と受入範囲

読み取りの Pull 診断はローカル追跡 ref を再確認し、外部で変更があれば状態の更新を求める。graft があり系譜を確認できない場合は候補を提示しない。ブランチ切り替えは無視対象と衝突したときに失敗し、元の HEAD・index・作業ファイルを保持する。合成 bare remote と仮の checkout で検証した。

独立 clone を空いている別パスへ公開する試作では、元の HEAD と index の SHA-256、編集済み・未追跡ファイルを保持し、候補で新 commit の tree と index の一致を確認した。元パスを退避してから候補を配置する試作では、その間で子プロセスを終了すると元パスが一時的に消えた。第三者がパスを確保した場合は配置を拒否し、退避版・候補・第三者の版を保持した。両方式の対象範囲と利用者への影響が異なるため、採用には製品承認が必要。

元の checkout で、外部 Git・エディタ・YMM4 による操作中も ref、index、作業ファイルを一貫して更新し、中断後に再開する契約は未成立。実 Pull の fast-forward、並行実行、timeout、権限不足、linked worktree 中断を受け入れたと解釈しない。読み取り診断にも、フィルター設定を確認してから別プロセスの `status` を開始する間に有効設定が変わる競合窓が残る。レビューでは設定固定または信頼境界の製品判断を次の条件とした。 [R18 Pull ADR](../architecture/adr/git-pull-recovery-r18.md)

## 保存とデータの保全

- 一覧は公開候補の物理 ID と SHA-256 を照合する。開始済みレシートを公開する前に同一操作の準備レシートを封印する。その間に子プロセスを終了したところ、2度の再確認とも Unknown となり、下書き・証拠・現用版を保持した。旧レシート v1〜v3 を読める。旧形式の証拠で結果を判定できない場合は手動確認に引き継ぐ。別ライターが一覧をロックして開けなかった場合は WPF から再試行でき、取り消しは同じパネルに表示する。固定ローカル NTFS、既存の対応属性と権限を前提とする。現用名の一時消失は別プロセスから観測できる。電源断後の永続化は未検証。
- 管理付き再リンクは、元ファイル、出力、候補、回復記録を通常ファイルのハンドルで確認し、検証したメタデータの各リビジョンを公開または再試行の終了まで保持する。元プロジェクトを変更せず、新規出力と版を確認する既存契約を維持した。非協調ライターが履歴ディレクトリに別の改訂を追加する場合や、旧履歴移行の作業ファイルへの同一権限の介入は境界外。ライブタイムライン変更は無効。
- YMMPX の新規作成は元の JSON と出力内の JSON を照合し、許可された素材パス変換を除く差分を拒否する。書き換えた参照ごとに元ファイルと同梱データのサイズ・SHA-256 を比較する。同サイズの別素材を合成パッケージに入れると従来は受け入れられ、修正後は拒否した。実 YmmpxLib による現行形式の作成、直接 DLL 読み出し、製品経路の抽出、同名素材、Unicode、無関連 JSON 項目を確認した。検証は素材ごとの読取時点に基づく。未参照の追加素材は ZIP 整合性のみ確認し、素材全体の一時点スナップショットは作成しない。検証中に素材が見つからない、読み取れない、変化した場合は公開せず、素材を確認してから再試行できる。
- 外部素材の検査は通常ファイルのハンドルを使い、親がない場合と権限・共有違反を区別する。素材一覧出力は新規作成専用。既存出力や競合側の作業ファイルを上書き・削除しない。素材の原本は読み取り専用で使用する。

## 再実行

隔離した YMM4 参照 DLL を `YMM4_PATH` に指定する。並行実行するプロセスごとに独立した短いディレクトリを `TEMP`、`TMP` に設定する。信頼済みの実 YmmpxLib ありの実行に限り、`YMMPX_LIB_PATH` に隔離 DLL を指定する。実ホストや共有 VM は今回使用していない。

```powershell
dotnet build .\YMMProjectManager.sln -c Release "-p:YMM4_PATH=$env:YMM4_PATH" --nologo
dotnet build .\YMMProjectManager.sln -c Debug "-p:YMM4_PATH=$env:YMM4_PATH" --nologo
dotnet run --project .\YMMProjectManager.Tests -c Release --no-build
dotnet run --project .\YMMProjectManager.Tests -c Debug --no-build
$env:YMM_TEST_FILTER = 'GitRemoteTests'
dotnet run --project .\YMMProjectManager.Tests -c Debug --no-build
$env:YMM_TEST_FILTER = 'ProjectListPublicationTests,ProjectListSaveTests,ProjectListIdentityRecoveryTests,AssetManifestTests,AssetInventoryTests,YmmpxFailureTests,RealYmmpxR5,OfflineControlsTests'
dotnet run --project .\YMMProjectManager.Tests -c Release --no-build
```

全回帰では `YMM_TEST_FILTER` を設定しない。個別件数は名前付き計測だけを数え、従来のネストした検証や明示スキップを成功件数に加えない。

| 構成 | 実 YmmpxLib | 終了コード | 成功グループ | 計測済み成功 | 失敗 | 明示スキップ | ランナー秒 |
|---|---|---:|---:|---:|---:|---:|---:|
| Release | あり | 0 | 62 | 93 | 0 | 1 | 68.157 |
| Release | なし | 0 | 62 | 93 | 0 | 2 | 68.470 |
| Debug | あり | 0 | 62 | 93 | 0 | 1 | 68.740 |
| Debug | なし | 0 | 62 | 93 | 0 | 2 | 68.126 |

MSBuild は Release 5.31 秒、Debug 5.42 秒、両方の終了コード・警告・エラーは0。R17 に比べ計測済み成功が各構成22件増。全構成の明示スキップに書き込み Pull が1件あり、DLL を指定しない構成は DLL 受入をさらに1件スキップする。隔離合成 Git の長いパスは環境の上限に達した際に未公開で停止し、所有済みの作業フォルダーを保持した。

同じコード HEAD の重点回帰は、実 YmmpxLib ありの Release 2回と Debug 1回で各80件成功、失敗・スキップは0。ランナーは28.521秒、28.504秒、28.420秒。Git は Debug と Release で各7件成功、失敗0、書き込み Pull の明示スキップ1件。ランナーは50.645秒、50.702秒。これらの実行間で合成 fixture は共有しなかった。

## 独立レビューと停止判断

レビューで、属性だけのディレクトリハンドルでは移動を妨げられないこと、一覧レシートのパスベースの処理、素材親欠落の判定、YMMPX の同サイズ別素材、WPF の取消通知先を指摘。式や名前の検査に加え、既存ハンドルの利用と失敗時の保全を合成テストに加えた。最終の関連差分には、追加の P0/P1 指摘はなかった。既存の Git 実効設定の競合窓は未解決。レビューはコード確認と隔離 NTFS の単独プローブで、統合スイートは Controller が実行した。

| 残件 | 今回試した内容 | 確認待ちの条件 |
|---|---|---|
| P0 書き込み Pull | 別パス公開、元パス退避中の子プロセス終了、外部 ref 変更の合成テスト | 許可された製品範囲と排他・再開契約の実証 |
| P1 Git 設定の競合 | 設定の観測と `status` が別プロセスであることを独立確認 | 有効設定を固定できる作業環境、または利用者承認を伴う診断の範囲 |
| 一覧、素材、再リンクの対応外 | 所有ファイルと親を固定し、中断・競合・履歴保持を合成検証 | 監査 SACL、一覧権限を持たず通過のみ許された親、電源断、ネットワーク FS、非協調で追加される履歴項目は別途契約が必要 |
| YMMPX 旧形式と実ホスト | 現行の実 DLL と合成入力で検証 | 旧形式の真正な fixture、隔離ホストと実認証 |

Git 障害の調査と並行して、上の独立して進められる保存・照合・UI 修正を統合した。残件を別々に確認した結果、既存承認の範囲で安全性を追加実証するには、上表の製品判断や環境が必要。未検証の動作は有効化せず、ローカルのチェックポイントに引き渡す。

## 再開順

1. ADR を確認して、既存 checkout を維持する要件と、別パスまたは管理対象 checkout を許可する条件を決める。後者を承認した場合は、プロジェクトの再関連付けと中断時の識別情報を定義し、専用の隔離 worktree で操作 ID を持つ試作を作る。既存パスを維持する場合は外部プロセスを含む書き込み主体の排他を先に実証する。どちらも最終判断は ref・index・作業ファイルの三点と回復を確認して行う。
2. 読み取り Git 診断の有効設定を固定または許可リストで隔離する設計を選ぶ。現行の dirty 判定を再現できない場合は、明示的な信頼確認の導入または診断項目を変える製品承認を得る。
3. 受入環境を用意し、実認証を伴う Git、実 YMM4 とライブタイムラインの契約、真正な旧 YMMPX、固定ローカル NTFS 以外に求める互換性を個別に検証する。予定の11月25日のレビューには現時点のコードと証拠を渡せる。11月24日までの全実装完了は、Pull の製品判断と受入結果に依存する。
