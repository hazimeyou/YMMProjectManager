# R21 GitHub とローカル Commit

## GitHub の認証境界

GitHub の認証方式を比較した。既存の Git 構成に任意の認証ヘルパーを委ねる方式は、リポジトリやシェル由来のヘルパーが入り得る。アプリ独自のトークン取得・保管方式は、秘密の管理責務を増やす。Git for Windows に同梱された Git Credential Manager（GCM）を Windows Credential Manager と組み合わせ、既に利用できる資格情報へのアクセスを操作単位で選ぶ方式を実装した。 [GitHub の GCM 認証資料](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git?platform=windows) [Git credential の優先順位](https://git-scm.com/docs/gitcredentials)

- 対象は資格情報やクエリを含まないリテラルの `https://github.com/owner/repository`。匿名が既定で、キャッシュ利用は明示選択を前提とする。
- Program Files 配下の標準 Git for Windows を用い、Git とキャッシュ認証時の GCM のファイルを保持する。GCM は GitHub のみに限定する。既存の任意ヘルパーを初期化し、親の `GCM_*` と一般的な GitHub トークン変数を引き継がない。
- GitHub の実行時は TLS を検証し、HTTP のリダイレクトと任意の URL 書換を許可しない。資格情報のリストやトークン、Git やヘルパーの生出力は UI に返さない。
- Clone、Fetch、Push の呼び出し時に認証方式を選ぶ。Pull は既存の承認証拠に方式を保持し、上流広告の確認と取得に同じ方式を使う。既存 R20 の ref、index、作業ツリー、回復記録の検証を用いる。
- アクセス確認は指定リポジトリに対する `ls-remote`。公開リポジトリの成功はアクセス可能を示す。アカウントのログイン状態や Push 権限は示さない。401 と403は別の失敗分類。GitHub の非公開リポジトリが返す404から、存在と権限の違いを確定できない。
- GCM のブラウザー・端末対話は無効。キャッシュのない利用者は承認済みのサインイン手順が必要。複数アカウント、SSO、GitHub Enterprise、標準以外の Git インストールは今回の確認範囲外。 [GCM の設定](https://github.com/git-ecosystem/git-credential-manager/blob/main/docs/environment.md)

Git for Windows 2.55.0.windows.5 と、同梱 GCM 2.9.1 のバージョンおよび有効な Microsoft 署名を読み取り専用で確認した。実アカウントや資格情報ストアにはアクセスしていない。合成試験は Git の `credential fill` をローカルの合成ヘルパーと組み合わせて動かし、匿名時の既定ヘルパー抑止、GitHub に対応する URL 範囲、他ホストの拒否、取消、401と403の分類、診断出力の除去を確認した。実 GitHub の公開・非公開ネットワーク受入は **NOT_VERIFIED**。

## ステージングと Commit

ステージするパスは個別ファイルとして選ぶ。フォルダー、リンク、Git の管理メタデータへの指定は拒否する。Git 本体の index 解析を使い、代替 index の予定 tree として変更を実体化する。通常の Git は `index.lock` を取得して書き込む。アプリはそのロックを保持し、予定 tree の検査に通った index を flush 後に同じディレクトリで発行する。仕掛中の Git 操作、既存 index の共有違反、特殊なファイル属性やアクセス方針は保存前に拒否する。ステージ解除は既存のステージから問題のファイルを外せる。初回 Commit 前の解除も同じ明示パスに限る。

Commit の確認画面に渡す情報は、リポジトリの物理識別、ブランチ、親 commit、予定 tree とステージ済み変更パス。確認後は最新 index から同じ tree を再確認し、既存の `index.lock`、HEAD の通常ファイル、進行中のマーカーを確認する。書き出した内容は `git commit-tree` に渡し、Git の ref ロック取得後にブランチ実体が通常 ref であることを再確認して、親 OID を条件に発行する。ブランチの実 OID を読み戻して結果を確認する。標準 Commit の完了に Push、amend、rebase は含まれない。フックと任意の署名プログラムは起動しない。設定上の必須署名がある場合は Commit を拒否する。 [Git update-ref のトランザクション](https://git-scm.com/docs/git-update-ref)

合成試験は明示パス、Unicode 名、未ステージ変更、初回 Commit、staged state の変化、中間取消、外部 ref 更新、同じ OID に向く symbolic ref、協調しない別プロセスが作った GIT マーカー、予定 tree の検査による拒否と旧 index の一致を検証する。Windows のローカル固定 NTFS と通常の Git ロックを守るプロセスを対象とする。外部ツールが Git のロックを無視して直接 `.git` を編集する場合と、電源断の耐久性は未検証。
