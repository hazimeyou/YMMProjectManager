## GitHub

Gitの公開・非公開Clone、Fetch、fast-forward Pull、非force Pushは、従来の承認と保存済みGCM資格情報を使う契約を維持する。Commit、Stage、ステージ解除は既存のローカル操作。キャッシュを使う場合は、利用者の明示操作でチェックボックスを有効にする。新しいログインや再ログインをアプリから起動する機能は利用不可。ローカルの合成HTTPS試験で、401、403、307を扱い分け、接続先の変更を拒否する。

調査対象の GCM 2.9.1の公式実装では、`github login --browser` はブラウザ認証してヘルパーのストアに保存できる。アプリでトークンを扱わないため第一候補になる。Git通信に適用するリダイレクト制限は、GCMのOAuthトークン交換に独立して適用されない。2.9.1と3.0.2のHTTPクライアントには、今回確認した範囲でリダイレクトの制約がない。対話CLIを隠す方式と独自OAuth／資格情報ストアへの切り替えは採用しなかった。再開時は、資格情報を含むヘルパー通信の宛先固定、リダイレクト拒否、ループバックとstateの検証、取消と再認証を確認する。候補に対し最初に隔離された子プロセスとネットワークの合成試験を行う。実アカウント受入は別途承認を得た専用リポジトリで行う。[GCMログイン実装](https://github.com/git-ecosystem/git-credential-manager/blob/6760f0ef069c994aa2bb1d703fb374986ee82a3e/src/shared/GitHub/GitHubHostProvider.Commands.cs#L59-L113) · [2.9.1のHTTPクライアント](https://github.com/git-ecosystem/git-credential-manager/blob/6760f0ef069c994aa2bb1d703fb374986ee82a3e/src/shared/Core/HttpClientFactory.cs#L53-L71) · [3.0.2のHTTPクライアント](https://github.com/git-ecosystem/git-credential-manager/blob/v3.0.2/src/Core/HttpClientFactory.cs#L52-L69)

## YMMPX素材受け渡し

1. 一覧から対象PFを選び「選択したプロジェクトを同梱」を実行する。PFのフォルダーを使い、必要に応じて追加のローカルフォルダーを指定する。
2. 素材名、参照場所、サイズ、SHA-256を確認し、素材ごとに許諾状態を選ぶ。「再配布許可確認済み」と「自作・権利保有」に限り同梱する。記録は利用者の申告として扱う。除外した素材や読取不能の素材の内容をコピーしない。
3. 新しい出力フォルダーを指定する。YMMPXと `ymmpm-transfer.json` を同じフォルダーに保持する。アプリから外部送信しない。
4. 受信側で「ymmpx展開」を使う。照合記録付き形式は構造、パッケージ全体、素材ごとの名前・サイズ・完全SHA-256を確認する。従来の形式は従来の展開経路で扱い、完全SHA-256の外部照合がないと表示する。展開先には既存の親の下の新規フォルダーを指定する。
5. 不足素材の表示を確認する。必要なら一覧に新しいプロジェクトとして登録する。展開時のPFの物理ファイル識別子とSHA-256に一致する場合だけ登録する。送信側のIdentityや履歴はパッケージに含めず、元PF・元素材・既存履歴を維持する。既存の管理付き再リンクの名前＋完全SHA-256条件を継続する。同梱されなかった素材はローカルの不足パスで表示し、受け渡し記録から管理付き履歴への自動移行や再リンクは行わない。

照合記録は破損や取り違えの検出に用いる。信頼できる配布元の本人性や、素材を再配布できることを証明する署名ではない。ZIPコメントを含めた通常のYMMPX構造と、別置きの照合記録を用いる。旧版は v0.2.1、v0.3.0、v1.0.1 の実リリースタグからCLIを再ビルドし、合成PFと素材で生成したパッケージに限定して検証した。他の旧版形式、既存利用者のアーカイブ、実YMM4への読込は別受入。Gitの検査は既知の記録・パス・素材・到達履歴を対象にし、文脈を取り除いた任意のコンテンツを特定できるという保証はない。

## 仕様調査と採用した境界

1. 上流 v1.1.0（6cff832c4648f43708a7305935c6303b61319a9d）の公開APIは、PFの `FilePath`、条件によってPSDの `EnableLayersFilePath` を参照し、`_ymmpx_project_path.txt`、PFと `links.json`、`resources/` をZIPに格納する。素材選択は除外リスト方式で、連番ファイルやPSD関連素材の処理も持つ。R23の厳格な許可リストを境界として使えるAPIとは確認できなかった。
2. 採用した方式は、同じZIP構造を管理側の許可リストで生成し、別置きの照合記録を追加する。ZIPコメントには照合記録の内容に結びつくハッシュを、照合記録にはパッケージ全体と個別素材のハッシュを保存する。内部に新しい必須ファイルを追加せず、上流リポジトリを変更していない。同名異内容も個別のディレクトリに元素材名で保存する。現行の実YmmpxLibで独立展開した。同名異内容、異名同内容は統合回帰に含めた。
3. 旧版のbasename形式では、受信PFの参照を検証済みのアーカイブ内の同名素材にだけ対応付ける。元パスを開かない。大小文字だけが異なる参照キーを含む曖昧な項目は拒否する。既存のPF整理は独立した機能として維持し、今回の受け渡し出力では上流の `RemoveUiSettings` を自動実行しない。
4. 互換なパッケージ本体を別製品に渡す場合、旧クライアントが補助記録を検証する保証はない。受信時にYMMProjectManagerを使えば、記録付き形式の欠落・不一致を検出する。既知のマーカーと名前空間をすべて除去した改変品は旧形式と区別できない。未知のPF情報は一般的なプライバシー除去の対象にせず保持する。
5. 同梱を安全に列挙できない連番PNGは不足として表示する。ローカルの選択範囲と普通ファイルを使用する。実NAS受入は今回の必須条件に含めず、素材プール自体の保存先仕様は維持する。

公開前の使用中断では原則として所有済み作業データだけを片付ける。Windowsのフォルダー移動では子ハンドルをいったん閉じる必要があるため、公開前と公開後それぞれに照合する。公開後に不一致を検出した場合は成功と一覧登録を拒否し、調査できるようフォルダーを保持する。安全な再試行は別の未使用フォルダーを選ぶ。検証ハンドルを閉じた後の外部プロセスによる変更と、電源断・ストレージ障害の耐久性は別の境界になる。
