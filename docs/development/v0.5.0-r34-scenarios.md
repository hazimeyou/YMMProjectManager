# R34 VM受入シナリオ

試験定義の版は `ymmpm-r34-v1`。本書は後続工程の審査用。実機の全項目は現在 `NOT_RUN`。環境、候補の固定、試験回数と証拠は [VM受入依頼書](v0.5.0-r34-vm-request.md) に従う。

## 全試験に共通する条件

- 各ステップに記載した操作を個別に承認する。実行時は `YMMPluginTest` の対話セッションと Medium Integrity を独立確認する。YMM4と候補は隔離ステージに置き、入力は合成データの新規コピーとする。ホストやゲストの本番領域、他プロジェクト、他Sceneを操作しない。
- シナリオや小項目ごとに新規Run IDを使う。既存の管理ハーネスに合わせ、上限案は一つのRunにつき合計120秒。そのうち終了と証拠の確定に8秒以上を確保し、通常操作は最大112秒とする。時間内に収まる手順単位を事前に定め、時間内に収まらない場合は別Runとして再審査する。
- 実行前にDLL・必要依存・対象PFのSHA-256と、既存入力・出力先の親ディレクトリの物理IDを記録する。新規出力先は開始時点で不在を確認し、公開後に出力の物理IDとSHA-256を記録する。ファイルを用いないRunでは理由付き `N/A` を記録する。入力と結果のログ、操作ジャーナル、対象PNGと診断PNG、終了コード、leaseとRecovery、HOST回収結果、隔離状態とQueueの前後比較をRun単位で保持する。
- 対象がゼロ件または複数件、ID・ハッシュ・セッションが変化、出力先が競合、所要時間超過、取消、結果不明のいずれかで次の操作を停止する。終了と回収は管理側の契約を使う。Recoveryが必要または結果が不明な場合は証拠と出力を保持し、管理側が終端状態・プロセス・lease・隔離を確認するまで再投入を止める。再試験は範囲・原因・対策を再審査して新規IDで実行する。

## A — 起動と画面認識

**R34-A01／導入確認・基準起動。** PF不要。管理側が審査し、承認されたYMM4 Liteと候補DLLを新規の隔離ステージに配置する。既存環境のプラグインは更新しない。配置先の物理ID、配置済み候補と依存のSHA-256、起動対象の一意性、試験ユーザープロファイルを開始前に確認して証拠に残す。

1. 隔離ステージからYMM4を起動する。
2. YMM4のツールメニューを開く。
3. 対象のプロセスにPM画面が既に存在しないことを確認し、一意に識別したYMMProjectManagerを1回だけ呼び出す。
4. 同一の対話セッションと起動プロセスの所有ウィンドウから新しくロードされた対象画面を認識する。ホスト内で表示する場合は、手順3の呼び出し開始から手順4の検証終了までに同一試行の一覧読込み開始・完了ログが新規に出たことを確認する。UIA階層差は許可済みの最小手順で扱う。別プロセスや類似名だけで採用しない。
5. 対象画面のPNGを取得する。失敗の診断PNGは種別を分ける。
6. YMM4を正常終了し、Worker終了、lease解放、Recovery不要を確認する。

タイトルまたは許容されたUIA識別子の根拠と所有プロセス、全6工程の時刻、対象PNG、YMM4とWorkerの終了コード0を証拠にする。多重起動や不一致は手順4以降を停止する。対象画面を閉じられない場合は管理側の終了・Recoveryへ移行する。R15第9回の枠を流用しない。

## B — YMMPX標準形式

**R34-B01／作成、R34-B02／展開、R34-B03／欠落・取消。** Aの成功、承認済みのYmmpxLib 1.1.0、試験用PFまたはパッケージ、書込み先が新規であることが前提。標準1.1・入手済みの旧版はそれぞれ別Runで確認する。

- B01で通常素材、連番PNG、PSD関連参照を含む試験PFを選択し、同梱一覧を確認して新規パッケージを保存する。RemoveUiSettingsの対象と非対象を事前に記録する。出力をローカルで検査し、PF・参照素材・意味のあるフィールドの保全、同梱内容と意図したUI設定処理の一致を確認する。
- B02で標準1.1と旧パッケージを別々の未作成出力先へ展開する。検証対象はPFのJSONと参照の対応、期待する素材のSHA-256、登録前の明示確認。未知の形式と安全範囲外の参照は安全に拒否または未解決と記録する。
- B03で素材欠落の事前表示、利用者取消、既存パッケージまたは展開先の競合を別々に確認する。既存ファイルと元PFのSHA-256が一致し、一時出力を製品の契約どおり扱うことが合格条件。

同梱確認、版、素材ごとのSHA-256、展開先と出力状態を証拠にする。元素材への書込み、既存場所への展開、外部送信、EXE作成・実行は禁止。出力の所有が不明な場合は保持し、管理側が隔離領域の所有を照合する。

公式ライブラリ単体で作った合成1.1アーカイブは、展開後の相対参照で欠落を照合する。欠落通知の受入ではPMで作成した受け渡し記録付きのアーカイブを用い、B03の作成前プレビューと別に観測する。

## C — 素材除外設定

**R34-C01／有効インポート、R34-C02／不正・競合。** Aの成功、試験PFと試験専用設定のコピーが前提。プレビューで局所・グローバル除外を確認し、有効なfixtureを明示承認後に取り込み、B01の候補表示で変化を確認する。不正設定では理由を表示して既存設定を保持する。公開競合の再現は合成障害テストを先行し、実機では承認した試験設定の変更操作に限定する。前後の設定SHA-256、選択素材、拒否理由、元PFと素材の一致を証拠にする。製品用設定の取込みと競合時の強制上書きは禁止。部分結果が残った場合は確認が終わるまで再取り込みを止める。

## D — Gitローカル操作

**R34-D01／初期化・選択Stage・Commit、R34-D02／拒否・取消。** Aの成功、別途承認されたGit実行ファイルと隔離ローカルrepo、素材を含まない合成PFおよび合成メタデータが前提。初期化後に差分を確認し、合成ファイル1件をステージ・解除・再ステージして明示確認付きCommitを行う。既知の素材のステージ拒否、取消で未承認変更が発生しないことも別Runで確認する。ref、index、worktree、ログと操作結果を記録する。アクセス先を設定しない。Remote、Push、ブラウザ認証、ネットワーク接続、ユーザー資格情報、強制更新、履歴書換えは禁止。実GitHub受入は通信と専用repoを別途承認した環境へ分ける。

## E — 64点サムネイル

**R34-E01〜E05。** Aの成功、短尺および目印付き長尺PF、同じScene IDの別版、複数SceneのPFと合成キャッシュが前提。前段階の証拠が確定してから次段階を審査する。

| ID | 操作 | 合格証拠 |
| --- | --- | --- |
| E01 | 保存済みPFを選び、既存キャッシュのギャラリーを開く | 元PFに対応するキャッシュだけを表示。選択を変えて旧結果を採用しない |
| E02 | 保存済みPFとロード済みSceneの対応を読取りで照合 | PF SHA-256・物理IDに加え、ホストが実際に観測したセッション・版・Scene。別版の拒否 |
| E03 | 独立Sceneの生成、描画資源の所有、解放を確認 | 開いているSceneとインスタンスが異なる。通常・取消・初期化失敗でVideoSource等の解放を観測 |
| E04 | 目印付きPFと1フレームPFから新規取得を各1回試す | 先頭・区間境界・終端の時刻と画像が一致し、上限64点。重複フレームの扱いを記録 |
| E05 | 生成中に選択を変更または取消し、別Runで再取得 | 未採用画像を破棄。再取得したPFのキャッシュだけを更新 |

E01は既存経路。E02・E03は読取りと検証用ハーネスの計画を事前承認する。E04・E05の実描画は独立Sceneと資源解放の契約実証、および有効化の別承認を前提とする。現候補で試験のために無効機能を強制解放する操作は行わない。Scene、シーク位置、dirty、Undo履歴、元PFが保たれることを前後証拠で確認する。

## F — プロジェクト比較

**R34-F01／合成画像、R34-F02／実描画。** 24 fps・約130秒の元PFと30 fps・約140秒の別版PFを使う。F01では合成画像を左右に表示し、共通シークを0、59.999、60、119.999、120秒、両側の終端へ動かす。固定値の負・正、および60秒から+10秒、120秒から−5秒の区間指定を入力する。区間開始を含めること、同じ共通時刻から正しいフレームに写像すること、範囲外側の空表示を記録する。試験設定を別名保存し、次のRunで読み直す。F02はE02・E03の実証と別承認後に同じ比較を実描画で検証する。両PFのSHA-256、左右フレーム目印、時刻・fps・表示例、設定SHA-256を保存する。編集中Timeline、両PF、Scene選択を変更しない。

F01は既存の合成WPFテストを基準とする。現候補で合成画像を供給できない実機手順は、別途承認した合成ハーネスを必要とする。F01を成立させるために実描画を有効化する操作は行わない。

## G — Timeline素材再リンク

**R34-G01／候補・適用前確認、R34-G02／直接反映の別ゲート。** 素材1点が欠落する合成PF、許可済みフォルダー内の名前＋SHA-256一致候補と、名前またはハッシュだけが一致する候補を使う。

- G01は候補を選択し、元名・完全SHA-256、PF物理IDと版、Timeline・項目ID、現在の参照パス、承認した候補の差し替えを照合する。別Scene、未保存編集または候補の競合時に拒否理由を確認する。別名PFへの既存経路は承認した合成出力先で検証できる。
- G02は別途実証されたホストの編集・履歴契約を前提とする。隔離した編集中PFの合成アイテムだけを対象に、Undo/Redo各1回、未保存編集の保全、setter途中失敗、項目差し替えとScene切替を個別に検証する。原子的編集または確認可能な巻戻しが成立するまでは直接反映を無効のまま扱う。

確認前後のID・版・ハッシュ、期待する状態、拒否・取消理由、履歴とdirtyを保存する。無関係な未保存編集を保存または破棄する操作、強制書込み、元PFや素材への上書きは禁止。不明時は再適用を止め、既存の別名PF操作へ案内する。

## H — 旧データ移行

**R34-H01／旧一覧とIdentity、R34-H02／旧世代の別名救済。** 旧スキーマと世代履歴を持つ合成データの専用コピーを使う。

- H01は重複プロジェクトIDの修復コマンドで同一性と残す項目を確認する。保存ダイアログでは「いいえ」を選び、`projects.recovered.json` を新規保存する。別Run用の隔離プロファイルにそのコピーを `projects.json` として置き、再読込する。曖昧な同一性と出力先競合を確認する。旧形式の原本のSHA-256を維持する。
- H02は「旧世代からPFを取り出す」で旧世代の `metadata.json` を開き、版、サイズ、SHA-256を照合して新規パスへPFを出力する。破損した旧Manifestを含む旧世代領域はそのまま保持する。更新の拒否は既存の合成回帰の対象。

前後のサイズ・SHA-256、旧／新のID、旧履歴と救済先のハッシュを保存する。旧データの直接上書き・自動削除は禁止。既存の回復記録を保持し、証拠不明時に移行を繰り返さない。

## I — キャッシュとログ

**R34-I01／使用量、R34-I02／完了キャッシュ削除。** Aの成功、専用ステージ内の完了済みキャッシュ・進行中の記録・無関係な番兵ファイル・合成ログが前提。設定画面で件数・サイズと場所を照合し、完了済みキャッシュだけを明示操作で削除する。キャンセル時は全ファイルを維持する。前後の一覧とSHA-256、表示と実際のサイズ、診断ログを保存する。進行中・所有不明・領域外のファイル、管理側証跡やログの自動削除は禁止。対象の入替えやアクセス拒否で中止し、専用領域と所有が確認できた場合のみ再試験する。

この4種の状態は、管理側が承認されたRun専用領域でセットアップする。完了済みキャッシュと進行中の記録は `SettingsAndDiagnosticsTests` の生成条件を参照し、セットアップ後に所有・状態・サイズ・SHA-256を確定する。番兵と合成ログも新規に作成して開始証拠に含める。
