# v0.5.0 R23 独立レビュー

Worker CがGit公開ガード、統合UI、展開・公開境界、GCMの公開ソースを確認した。Worker Aも、認証作業とは独立した担当としてYMMPXの読取境界と許諾・形式整合性を確認した。統合の判断と修正はControllerが担当する。

| 優先度 | 指摘 | 対応・検証 |
|---|---|---|
| P0 | アプリ内GCMブラウザログインのOAuth通信で宛先変更を制約する契約が未確認 | 初回・再ログインを有効化せず、固定接続先に対する保存済み資格情報の経路を維持 |
| P1 | 展開完了から一覧登録の確認中に同内容の別PFへ差し替わり得る | 展開中に記録した物理IDとSHA-256を照合し、読取保持しながら一覧に保存。WPF合成fixtureで同内容差し替え、取消、一覧保存失敗後の差し替え拒否と元実体を戻した際の再試行を確認 |
| P1 | 作業領域の素材・照合記録が最終公開前に置換され得る | 厳格展開の公開前に対象ツリーを照合。Windowsでは子ハンドルを閉じてrenameし、公開後に全対象のハンドルを保持して物理IDとSHA-256を再照合。公開後に不一致を検出した場合は成功・登録を拒否し、フォルダーを保持 |
| P1 | 許可ルートの大文字小文字の扱いが、Windowsの大小文字区別ディレクトリと一致しない | ルート比較にOrdinalを使用し、大文字と小文字の異なる経路の暗黙承認を拒否 |
| P1 | 同じフォルダーに別の照合記録があると従来形式を拒否する | 転送用マーカーまたは予約済み名前空間で振り分け |
| P2 | 無効なWindowsの保存先名や、同梱不可の素材に対する許諾入力が表示される | UIと保存処理の両方で保存先を検証し、除外理由を表示。同梱不可の行の許諾を編集不可に設定 |
| P2 | 受信照合記録の許諾欄は送信者申告で、法的許諾や出所の証拠にできない | データの一致と送信元・権利の証明を区別して引き継ぎに明記 |
| P3 | 任意のファイルの名前・内容・周辺文脈をすべて変えた場合の自動検出には限界がある | 既知の素材の完全SHA-256、予約済みの名前空間、記録の構造、到達履歴を検査する範囲を記録 |

実YMM4、実アカウントのログイン、実NASへのアクセス、正式な受入はレビュー対象外。Gitの外部送信試験には隔離bare repositoryまたはHTTPSループバックを使用した。
